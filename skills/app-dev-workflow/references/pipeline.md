# 全流程详解（S0–S7 与门禁 G0–G7）

本文件是流程的"地图"。执行任何阶段前：读对应小节 + `knowledge/checklists.md` 的门禁清单 +
`knowledge/lessons.md` 中该阶段的既有经验。

## S0 受理（intake）

**目标**：把任何形态的需求（一句话灵感 / 聊天记录 / 正式 PRD）变成有 ID、有记录、可追溯的工作流（WS）。

**入口条件**：无（任何需求都从这进）。

**步骤**：
1. **原样记录**：把需求原话引用进 intake 的"原始需求"栏，不改写、不翻译、不"帮忙总结掉细节"——
   后续所有理解分歧都以原话为锚点。
2. **补背景**：记录提出人、时间、动机（为什么要这个功能）。
3. **一次性澄清**：把问题集中一次问全（目标用户 / 平台 / 技术栈约束 / 期望节点 / 成功标准），
   问答记入 intake 的"澄清问答"栏。得不到答案的问题列入"未决问题"，不臆测。
4. **分类定级**：类型（feature / bugfix / optimization / refactor）× 规模（S≤1天 / M≤1周 / L>1周）。
5. **查重与关联**：查 `INDEX.md`，看是否有语义重复或强相关的 WS，有则在双方 intake 中互相引用。
6. **创建 WS**：生成 `WS-yyyymmdd-slug` 目录（用 `scripts/af.sh new` 或按 trace-spec 手工），
   注册进 INDEX，timeline 写第一条。

**产出**：`00-intake.md`、INDEX 注册条目、timeline 首条。

**G0 门禁要点**：目标一句话说得清；有初步验收标准（哪怕粗）；类型规模已定；查重已做。

**常见坑**：把灵感直接当设计开工（见 lessons.md 标签 `阶段:受理`）。

## S1 产品设计（design）

**目标**：把 intake 变成"三方（产品经理/开发/UI/UX 设计）都能照着干活"的详细设计文档。

**入口条件**：G0 已过。

**步骤**：
1. **开工前**读 lessons.md 中 `阶段:设计` 的条目。
2. **现有系统调研**：设计与实现都不能凭空。调研相关系统的代码与文档（可派 Explore 子 agent），
   结论写入设计文档"现状与约束"。**不清楚的存量行为，宁可读码确认，不可想当然。**
3. **功能 / 功能设计**：核心循环、用户动线、状态流转（用文字状态机或伪代码描述皆可）。
4. **交互流程**：页面跳转清单、操作与反馈（每个操作必须有可感知的反馈）。
5. **参数设计**：每个参数给 **默认值 + 合理区间 + 极端值行为**。没有区间的参数等于把坑留给 QA。
6. **边界与异常**：网络异常与重试、并发编辑冲突、数据为空 / 超限、重复提交、跨时区 / 权限差异等，逐条列出处理方式。
7. **依赖系统清单**：要动哪些现有系统、是否影响其他功能，影响面写明。
8. **文案**：页面文案、toast、报错信息（占位文案标注 `TBD-文案`，不得默认"暂无"）。
9. **UI 需求点表**：单独成节，是给 UI/UX 设计（S2B）的唯一输入接口：页面清单、每页面的元素与状态、动效意图。
10. **性能预算**：关键路径的预算（首屏可交互 / 包体积 / 接口 P95 / 内存峰值），写不出就写"未定+跟进人"。
11. **风险清单**：技术风险、设计风险、依赖风险，各附缓解方案。
12. **验收标准编号化**：`DS-1, DS-2, ...`（Design Specification），每条可执行验证。
    **这组编号是 S5 QA 用例推导的唯一来源**，质量决定测试质量。
13. 过程中的重要取舍写成决策记录 `decisions/D-xx`（为何选 A 不选 B，日后复盘的依据）。

**产出**：`01-design.md`、必要的 `decisions/`。

**G1 门禁要点（默认人工确认）**：三方视角各过一遍（产品经理完整性 / 开发可行性 / UI/UX 设计可做性）；
未决问题 ≤3 且各有负责人与节点；所有参数有默认值与区间；验收标准覆盖核心功能与主要边界；
依赖系统的影响面已被相关模块确认。

**常见坑**：文档里出现"等等 / 之后再定 / 类似就行"（见 lessons L-002）。

## S2A 任务拆单（breakdown）

**目标**：把设计文档映射为**可独立验收、依赖明确、可并行**的任务卡集合。

**入口条件**：G1 已过。

**拆单原则**：
- 一张卡 = 一次可独立验收的最小交付。粒度基准 0.5～2 人日；超过 2 天的卡必须再拆。
- **视图与逻辑分卡**：数据 / 逻辑层一张卡，体验层（UI 绑定、动效挂接）另一张卡。
  UI/UX 设计改版时才不会牵连逻辑（见 lessons L-003）。
- **公共底座先行**：配置表结构、数据接口、公共组件这类"大家都依赖"的任务单独成卡、排最前、串行做。
- 每张卡必须写清**验收标准**（引用 DS 编号或具体可执行步骤）与 **touches-files**（预计修改的文件，
  用于并行互斥检查）。

**步骤**：
1. 逐节读设计文档，为每节产出任务或写明"不适用"（G2 会核对覆盖度）。
2. 标 DAG 依赖（A 依赖 B）与并行组（同一波可同时开工的卡）。
3. 估时：每卡给 `乐观值/现实值` 两个数（复盘要用）。
4. 生成任务卡 `tasks/T##-slug.md`（模板见 templates/task.md），任务板汇总。
5. 任务板标记初始状态：无依赖的卡置 `ready`，其余 `backlog`。

**产出**：`02-task-board.md`、`tasks/T##.md`。

**G2 门禁要点**：设计文档每一节都能指到任务（或书面"不适用"）；DAG 无环；每卡有验收标准、
估时、touches-files；并行组内无文件冲突；总量与设计范围一致（不多不少）。

**增量拆单**：S3/S5 中途发现缺卡（含UI/UX 设计回流的配合需求），主控补卡并在 timeline 记录补卡原因，
不算违规；**不补卡直接写码才算违规**。

## S2B UI/UX 设计（art）——与 S2A 并行

**目标**：基于设计文档的 UI 需求点表，产出开发可照着接入的 UI / 动效 / 视觉反馈设计。

**入口条件**：G1 已过（与 S2A 相同，两者只依赖设计文档，互不等待）。

**步骤**：
1. **风格基准**：参考图 / 竞品截图 / 既有风格规范链接，定调性。
2. **响应式与适配**：设计基准宽度（如 1440 / 768 / 375）、断点与栅格、极端窗口尺寸与安全区（刘海屏 / 最小窗口）。
3. **页面设计**：逐页面给出布局说明（分区、层级、栅格与关键约束）、元素状态（普通/悬停/按下/禁用/选中/红点）。
4. **动效设计**：逐条列触发时机、时长、缓动曲线、**是否可跳过**、断线/降级时的体验。
5. **视觉反馈设计**：loading / 空态 / 错误态 / 骨架屏的触发点、时长、性能开销与层级。
6. **设计资产清单**：命名规范、导出规格（格式/尺寸/压缩）、目标目录——这是给开发接入与后续外包的契约。
7. **对齐检查**：逐条核对 UI 需求点表，确认全覆盖；发现设计文档矛盾/缺漏 → 报回主控走设计变更（D-xx），
   **UI/UX 设计不得自行脑补功能语义**。
8. 若需要开发配合的工具/接口（如导表、预览器）→ 提需求给主控，回流 S2A 增量拆单。

**产出**：`03-design-visual.md`（可附产出物文件链接）。

**G2' 门禁要点**：UI 需求点表逐条对齐；每个动效/视觉反馈有时长与触发定义；性能预算明确且不超 S1 预算；
设计资产清单命名与目录符合项目规范（CONFIG.md）。

## S3 任务实现（implement）

**目标**：按卡实现，卡卡闭环，全程可追溯。

**入口条件**：目标卡状态为 `ready`（其依赖卡全部 `done`）。

**单卡流程（每张卡都必须完整走完）**：
1. 读任务卡 + 该卡涉及模块的 lessons 条目；读 touches-files 相关现状代码。
2. 领卡：状态 `ready → doing`，timeline 记录。
3. 实现。**范围纪律：只做卡上的事**。发现必须顺带改的公共代码 → 先做公共部分单独成卡/或报主控，
   不默认"顺手改了"。
4. 按卡的验收标准逐条自测，把**证据**（命令输出 / 截图 / 日志摘要）记入任务卡。
5. 提交：`[WS-yyyymmdd-slug][T##] 摘要`；一个任务尽量一个提交，大了拆提交但都带同一前缀。
6. 回填任务卡：变更文件清单、commit hash、实际耗时、踩坑备注（复盘的原料）。
7. 状态 `doing → review`，timeline 记录；主控（或指定评审者）核对后置 `done`。

**并行规则**：同一并行组内、touches-files 无交集的卡可同时派发（详见 multi-agent.md §4）。

**阻塞处理**：卡住超过 30 分钟（人）或连续 2 次尝试失败（AI）→ 状态 `blocked`，
任务卡写明阻塞点与已试方案，主控决策（换人 / 换方案 / 升级设计问题）。

**G3 门禁要点（逐卡）**：验收标准逐条满足且有证据；无未声明的范围扩张；提交信息带 ID；
任务卡回填完整；timeline 有该卡状态流转记录。

## S4 联调与体验接入与调优（integrate）

**目标**：把UI/UX 设计产出接入逻辑，调到"能上线"的体验与交互体验，且**调优过程可复现**。

**入口条件**：相关逻辑任务 `done` + UI/UX 设计/设计资产齐备（G2' 已过）。

**步骤**：
1. 列**接入清单**：页面挂接、数据绑定、动效触发点、视觉反馈挂点、提示音位——逐项对照 03-design-visual.md。
2. 逐项接入，每完成一项在 integration-log 打勾并记录问题。
3. **调优会**（可人机协同）：每次调参必记录——参数 / **前值** / **后值** / 理由 / 观察到的效果。
   没有前值记录的调优视为未发生（见 lessons L-005）。
4. 性能与交互体验验收：首屏可交互、包体积、接口 P95、内存峰值、操作反馈延迟，对照 S1 性能预算。
5. 遗留占位资源逐项登记（谁、何时补），不允许"隐式占位"。

**产出**：`04-integration-log.md`。

**G4 门禁要点**：接入清单全勾；调优记录完整；性能达标或偏差已登记原因；无未登记的占位资源。

## S5 QA（qa）

**目标**：验证的是**设计文档**（DS 编号），不是开发的自我描述。

**入口条件**：G4 已过；**设计冻结**（QA 期间的变更走 D-xx 例外审批或新 WS）。

**步骤**：
1. 用例推导：每条 DS 验收标准 ≥1 条用例；S1 的边界与异常清单逐条转用例。
   **禁止从实现代码反推用例**（实现怎么写的就怎么测 = 测不出实现之外的错，见 lessons L-006）。
2. 冒烟：核心动线跑通才进入全量。
3. 全量执行，用例结果逐条记录（通过/失败/阻塞/不适用）。
4. BUG 走 `bug` 指令：登记 `BUG-xxx` → 修复（修复卡走 implement 流程）→ 回归验证 → 关闭。
5. 回归：BUG 修复后重跑受影响用例 + 冒烟。
6. 出测试报告 `05-qa/QA-Rxx.md`。

**G5 门禁要点（默认人工确认）**：用例 100% 执行；P0/P1 BUG 清零；P2/P3 每个有明确处置决定
（修 / 延期带去向）；回归通过；**根因分类为"流程性"的 BUG 已产出经验条目**（强制回流点）。

**BUG 严重级定义**：P0 崩溃/卡死/数据丢失/计费错误；P1 主功能不可用且无绕行；
P2 主功能异常但有绕行 / 次要功能不可用；P3 体验瑕疵。

## S6 落地合入（ship）

**步骤**：
1. merge 前检查：timeline 完整、G0–G5 全过、WS 目录内无 TODO 级未决（或已转任务/BUG）。
2. 合入（PR 描述附 WS 目录路径与一句结果摘要，让未来的自己 3 秒看懂这次交付）。
3. 更新项目 changelog（如有）；打 tag（如有版本管理）；清理分支。
4. WS 状态 `ship`，timeline 记录 merge commit hash。

**G6 门禁要点**：G0–G5 全部有记录地通过；merge commit 与 WS 互相可查；复盘已排期
（**复盘可以在 merge 后立即做，但不允许 WS 在复盘前关闭**）。

## S7 复盘沉淀（retro）

**目标**：把这次 WS 变成团队的资产。详细步骤见 operations.md §10，此处只列框架。

1. **数据**：每卡 估时 vs 实际（偏差 >50% 的必须归因）；BUG 数按严重级 / 根因 / 发现阶段分布；
   并行度实际利用情况（计划并行组 vs 实际串行化的卡及原因）。
2. **三问**：什么做得好要保持？什么踩了坑要避免？流程哪里要改（改模板 / 清单 / 规范 / 经验库的哪一页）？
3. **经验分流**：通用 → skill 的 lessons.md（L-xxx）；项目级 → 项目的 `.appflow/LESSONS.md`。
4. **改进项**：每条有负责人与节点，登记进任务板或 backlog。

**G7 门禁要点**：≥1 条经验入库或有书面"无经验可沉淀"说明；偏差归因完成；
涉及 skill 修改的已在 CHANGELOG.md 登记；WS 可置 `closed`。

## 附：跨阶段规则

- **任何阶段发现设计问题**：不私改，报主控 → 走决策记录（小）或设计变更 + 影响面评估（大），
  受影响任务卡暂停并标注。
- **暂停 / 取消**：WS 任意状态可 `paused`/`cancelled`，timeline 必须记录原因与恢复条件；
  `cancelled` 的 WS 保留全部痕迹（未来类似需求的第一手参考）。
- **一人多角**：允许，但主控视角必须独立审查执行产出（自己写的卡自己审 = 没审），交接契约不变。
