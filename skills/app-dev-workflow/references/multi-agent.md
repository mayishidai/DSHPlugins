# 多 Agent 编排规范（并行 / 串行 / 冲突 / 失败）

本规范同时适用于"多 AI 子 agent"与"多人 + AI 混合团队"——因为所有交接都走文件，
谁是血肉谁是硅基对流程不可见。

## 1. 编排总则

1. **单主控原则**：任何时刻一个 WS 只有一个主控。`INDEX.md`、`02-task-board.md`、
   他人任务卡、WS 状态机——只有主控能写。子 agent 越权写这些文件 = 无效操作，主控回滚并留痕。
2. **文件交接原则**：子 agent 之间不共享对话记忆，一切信息经 WS 目录文件传递。
   子 agent 的产出必须落文件，"在对话里汇报了"不算交付。
3. **自包含派发原则**：主控派发时，提示词必须完整注入（模板见 §3），
   不得假设子 agent 知道任何上文。
4. **粒度原则**：一个子 agent = 一张任务卡（或一个UI/UX 设计模块 / 一轮 QA）。
   禁止一个子 agent 跨多卡操作（尤其跨并行组的卡）。

## 2. 并行 / 串行调度图

```
intake(S0) → design(S1)
                 │ G1
        ┌────────┴────────┐
        ▼(并行)            ▼(并行)
  breakdown(S2A)      art(S2B)          ← 两路只依赖设计文档，同时派发
        │ G2              │ G2'
        └───────┬─────────┘
                ▼
   implement(S3)：按 DAG 分波派发
     波次 = 拓扑排序的"就绪层"（依赖全 done 且互不冲突的卡）
     示例：[T01 公共底座] → [T02 T03 T04 并行] → [T05 T06 并行] → [T07 接入准备]
                │ G3 逐卡
                ▼
   integrate(S4)：单一开发 agent 收口（串行，需要全部前置齐备）
                │ G4
                ▼
   qa(S5)：QA agent 执行；发现的 BUG 由主控登记，
           修复卡可多路并行（同 S3 波次规则），回归由 QA agent 收口
                │ G5
                ▼
   ship(S6) → retro(S7)：主控串行
```

**判并行三条件（缺一不可）**：依赖已满足（DAG）∧ touches-files 无交集 ∧ 验收可独立判定。
不满足就串行——**串行不是失败，返工才是**。

## 3. 子 Agent 派发提示词模板（主控必须按此结构注入）

```
你是「<角色>」，为工作流 <WS-ID>（<一句话需求>）工作。

## 第一步：开工前必读（按序）
1. 本 skill 的 references/roles.md 中「<角色>」章程（职责/禁做/准则）
2. <输入文件清单，含路径>
3. references/knowledge/lessons.md 中标签含「<阶段>」的条目

## 任务
<具体任务描述；若是任务卡：完整粘贴任务卡内容>

## 边界（硬约束）
- 只允许写这些文件：<明确清单>；禁止修改 INDEX.md / 02-task-board.md / 其他任务卡
- 代码提交信息格式：[<WS-ID>][<T##>] 摘要
- 只做任务范围内的事；发现卡外问题 → 写入产出文件的"发现与建议"节，不顺手处理
- 阻塞判定：连续 2 次尝试失败即停止并在产出中写明已试方案，不要硬编

## 产出要求
- 按模板写入：<输出文件路径>
- 完成后输出摘要：状态(done/blocked) + 做了什么 + 证据（命令输出/文件路径）+ 遗留问题
```

## 4. 冲突规则

- **派发前互斥检查**（主控责任）：即将并行的卡两两比对 touches-files；
  有交集 → 串行化（标依赖）或合并为一卡。**公共配置表 / 公共组件类文件默认高危，
  涉及它们的卡一律串行**（见 lessons L-004）。
- **运行中新增文件**：执行者实际改了 touches-files 之外的文件 → 立即回填任务卡并报主控；
  若与他卡撞上 → 后提交者停下，主控裁决（rebase / 串行重做）。
- **任务板锁**：并行期间任务板状态列由主控统一更新，子 agent 只在自己卡内写状态日志。
- **UI/UX 设计回流**：art 期间产生的开发配合需求 → 只能经主控增量拆单，UI/UX agent 不得直接给开发 agent 派活。

## 5. 失败与超时处理

| 情形 | 处理 |
|---|---|
| 子 agent 执行失败 / 输出不合模板 | 主控不直接重试原提示词：先补上下文（缺了什么信息导致失败），再重派；连续 2 次失败 → 任务 `blocked`，换方案或换执行者 |
| 子 agent 越权写了禁写文件 | 主控回滚该文件（git），timeline 记录越权事实与原因，重派时强化边界 |
| 任务阻塞 >1 个工作日 | 主控必须处置：拆小卡 / 换人 / 升级为设计问题 / 暂停 WS 并记录 |
| 并行撞车已发生 | 以先提交者为准，后者基于前者重做差异部分；两者都记 timeline |
| 执行者是人 | 同样规则：阻塞即标 `blocked`，AI 主控在 timeline 追踪并定期提醒 |

## 6. 人工介入点（默认配置，CONFIG.md 可改）

| 门禁 | 默认 | 原因 |
|---|---|---|
| G1 设计评审 | **人工确认** | 设计质量决定下游全部成本，且含价值判断 |
| G5 发布验收 | **人工确认** | 上线风险承担在人 |
| 其余门禁 | AI 主控自检 + 留痕 | 机械性检查，AI 可靠 |

人工门禁的执行方式：主控汇总门禁清单与证据 → 请用户逐项确认 → 用户答复记入 timeline
（谁、何时、通过/打回及意见）。**用户未答复前视为未通过，主控不得自行推进。**

## 7. 一人多角 / 人机混合的补充规则

- 同一 AI 会话先后扮演主控与执行角色时，切换角色必须显式声明（timeline 记"角色切换"），
  且执行产出仍需以主控视角重新审读后再过门禁。
- 人执行任务卡时，AI 负责提醒流程（提交前缀、回填字段），不代人填写自测证据。
