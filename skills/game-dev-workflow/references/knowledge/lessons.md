# 经验库（lessons）——只追加，不改写历史条目

**写入规则**：新条目编号 = 当前最大 L-### + 1，永不复用；与既有条目同义时不重复开条，
在旧条目下追加"补充案例"。通用判定：去掉项目名仍成立 → 本库；否则入项目的 `.gameflow/LESSONS.md`。
每条必须带来源（WS / BUG / 复盘）。修改本文件须登记 skill 的 CHANGELOG.md。

**条目格式**：

```
## L-### | 一句话标题
- 日期 / 阶段 / 角色 / 标签：`阶段:xx` `标签:xx` / 来源：WS-xxx
- **情境**：什么背景下踩的坑
- **教训**：错在哪、代价是什么
- **对策**：下次具体怎么做（可执行）
```

## L-001 | 数值无边界 = 把坑留给 QA
- 2026-09-13 / 设计 / 策划 / `阶段:设计` `标签:数值` / 来源：种子（初始示例，待真实复盘覆盖）
- **情境**：设计文档只写了"每日刷新价格上浮"，没写浮动的上下限和极端叠乘后的结果。
- **教训**：实现各自解释边界，QA 阶段刷出离谱数值，三方对"是不是 bug"争论两天。
- **对策**：设计文档中每个数值必须给三件套——默认值、合理区间、极端值行为（G1 检查项）。

## L-002 | 文档里的"等等"就是未来的 BUG
- 2026-09-13 / 设计 / 策划 / `阶段:设计` `标签:文档质量` / 来源：种子
- **情境**：设计文档多处出现"等等""之后再定""类似 XX 就行"，开发按各自理解填补。
- **教训**：模糊表述在三个角色脑中是三个设计，返工量远超把话写清楚的成本。
- **对策**：含糊处一律显式进"未决问题"（带负责人与节点）；未决 >3 项不得过 G1（门禁项）。

## L-003 | 表现与逻辑必须分卡
- 2026-09-13 / 拆单 / 程序 / `阶段:拆单` `标签:架构` / 来源：种子
- **情境**：商店的购买逻辑与界面绑定写在同一张任务卡、同一批文件里，美术中途改版 UI。
- **教训**：改版牵连逻辑重测，并行开发也做不起来——美术与程序无法各走各路。
- **对策**：拆单时数据/逻辑层与表现层（UI 绑定、动效挂接）强制分卡分文件（拆单原则）。

## L-004 | 并行任务改同一配置表必撞车
- 2026-09-13 / 实现 / 程序 / `阶段:实现` `标签:并行` / 来源：种子
- **情境**：两张并行任务的 touches-files 都包含全局配置表，后提交者覆盖了前者的字段。
- **教训**：公共资源上的"并行"实际是串行+互相破坏。
- **对策**：公共配置表/公共组件类文件默认高危，涉及它们的卡一律先行串行（互斥检查规则）。

## L-005 | 没有前值记录的调优等于没调
- 2026-09-13 / 接入 / 程序 / `阶段:接入` `标签:调优` / 来源：种子
- **情境**：手感调优会上反复改参数，一周后想回到"那天手感最好的版本"，没人记得数值。
- **教训**：不可复现的调优在版本迭代后全部归零。
- **对策**：调优记录表强制四要素：参数/前值/后值/理由（+观察效果），缺前值视为违规（铁律 3 延伸）。

## L-006 | 用例从设计推导，不从实现反推
- 2026-09-13 / QA / QA / `阶段:QA` `标签:测试` / 来源：种子
- **情境**：测试同学直接照着实现代码写用例，代码里没处理的分支自然也没被测到。
- **教训**：用例覆盖度上限被实现锁定，设计里写明但实现遗漏的行为全部漏网。
- **对策**：每条用例必须溯源 DS 编号或边界清单条目；QA 发现 DS 没写的行为异常，按设计缺口报 BUG。

## L-007 | QA 期接受需求变更 = 回归范围失控
- 2026-09-13 / QA / 主控 / `阶段:QA` `标签:变更管理` / 来源：种子
- **情境**：QA 第三天"顺手"加了个小需求，已跑完的用例全部失去效力但没人重跑全部。
- **教训**：一次小变更让全部已通过结果作废，发布延期且没人说得清测过什么。
- **对策**：QA 期设计冻结；变更走 D-xx 例外审批并明确回归范围，或转入新 WS（门禁与禁令）。

## L-008 | 估时偏差大的任务必藏流程问题
- 2026-09-13 / 复盘 / 主控 / `阶段:复盘` `标签:估算` / 来源：种子
- **情境**：复盘时发现超时最多的几张卡，根因都不是"写得慢"，而是设计缺口或依赖未就绪。
- **教训**：估时偏差是流程问题的温度计，不归因就会在下个 WS 原样复发。
- **对策**：偏差 >50% 的任务复盘强制归因（G7 检查项），归因结论回写拆单原则或经验库。

## L-009 | 多 agent 并发写同一文件：写前重读 + 分区 + diff 自检
- 2026-09-29 / 实现 / 程序 / `阶段:实现` `标签:并行` `标签:多agent` / 来源：用户反馈（v1.2.1 增补 multi-agent.md §5）
- **情境**：多 agent 并行时两张卡的改动落到同一文件（公共配置表 / 注册表 / barrel 导出文件），
  后写者基于派发时的旧快照整段重写，把先写者已落地的改动直接吞掉。
- **教训**：AI 团队成员之间是**约定级**并发，没有系统级文件锁——"派发前互斥检查"只能挡住
  **已知**的 touches-files 交集，挡不住运行中越界、共享文件的追加需求、以及编号并发取号撞车；
  一旦覆盖，diff 里往往只剩"少了什么"而看不出是谁干的。
- **对策**：并发写同一文件必须套**四道防线**，缺一道就退回串行——
  ① 主控为每个成员划定互不重叠的可写区段（其余只读）；
  ② 只追加 / 改局部值，禁止整文件重写、格式化、跨区重排（重排会让另一方的行号锚点失效）；
  ③ 写前重读磁盘最新内容（不基于派发快照），改完复核自己那段的 diff；
  ④ 提交前 `git diff <文件>` 自检只含自己的改动，撞车以先提交者为准、后者基于最新内容重做差异。
  追加式文件（timeline / LESSONS）另守三条：ID 取号主控独占、只许尾部追加、格式与署名一致。
