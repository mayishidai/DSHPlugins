# 多 Agent 编排规范（平台自适应 / 并行 / 串行 / 冲突 / 失败）

本规范同时适用于"多 AI 子 agent"与"多人 + AI 混合团队"——因为所有交接都走文件，
谁是血肉谁是硅基对流程不可见。

**本 skill 不绑定任何单一平台**：它会在 CodeBuddy、WorkBuddy、deepseekharness、hermes、
openclaw 等不同宿主下被调用，各家的多 agent 能力（甚至有没有）并不相同。
因此**契约跨平台一致，实现按当前平台能力自动抉择**——见 §2 的平台探测与档位映射。

## 1. 编排总则

1. **单主控原则**：任何时刻一个 WS 只有一个主控。`INDEX.md`、`02-task-board.md`、
   他人任务卡、WS 状态机——只有主控能写。子 agent 越权写这些文件 = 无效操作，主控回滚并留痕。
2. **文件交接原则**：子 agent 之间不共享对话记忆，一切信息经 WS 目录文件传递。
   子 agent 的产出必须落文件，"在对话里汇报了"不算交付。A 档团队成员之间的消息
   只是**通知**，不是交付——交付以文件落盘为准（见 §2.5.4 收割纪律）。
3. **自包含派发原则**：主控派发时，提示词必须完整注入（模板见 §4），
   不得假设子 agent 知道任何上文。B 档（仅子代理）尤其要一次写到底——没有追问渠道。
4. **粒度原则**：一个子 agent = 一张任务卡（或一个美术模块 / 一轮 QA）。
   禁止一个子 agent 跨多卡操作（尤其跨并行组的卡）。
5. **多 agent 优先原则**：在**具备派发能力的平台**（§2.2 探测为 A / B 档）上，凡 §3 调度图
   标"并行"的环节、凡 operations.md 标注"默认多 agent"的指令，**必须**派发多 agent 执行——
   **能多 agent 执行的都多 agent 执行**。主控不得以"顺手做了更快"为由自己串行包办：
   主控抢执行者的活 = 主控上下文爆炸 + 并行度数据失真 + 复盘无据。
   仅以下情形允许退化单 agent 顺序执行，且必须在 timeline 记录退化原因：
   - 平台无派发能力（探测为 C 档）或环境中无可写权限的执行者类型；
   - WS 全程无可并行点（单卡、无独立美术与 QA 环节）；
   - 用户明确要求不开多 agent；
   - 任务本质强制串行（如 S4 收口）——串行不是失败，返工才是。

## 2. 多 agent 执行：平台自适应

### 2.1 第一原则：能力决定形态，不写死平台

- 角色、派发、交接、收割的**契约在任何平台都相同**（都走文件）；
  变的只是"用什么机制把活派出去"。
- 主控开工第一件事：**平台探测**（§2.2），把档位记进 timeline，之后一律按档位执行。
- "能多 agent 执行的都多 agent 执行"这条**不变**：在 A / B 档是硬性要求；
  在 C 档（平台无派发能力）自然不适用——按顺序执行并留痕，**不算违规**。

### 2.2 平台探测：三个能力档位（判据是工具，不是平台名）

主控按下列顺序自检当前环境**实际可用**的工具，命中即停：

| 档位 | 判据 | 含义 |
|---|---|---|
| **A 团队模式** | 能启动**具名、长期存活、可互相通信**的成员（可 respawn、历史持久） | 最强：角色可长期分工、可中途追问、可并行推进 |
| **B 子代理模式** | 只能派发**一次性子代理**（有派发能力，但成员不长期存活 / 无成员间消息通道） | 中等：能并行，但只能靠文件交接 |
| **C 单 agent** | **没有任何派发能力** | 主控顺序扮演各角色，切换须显式声明 |

判据只看**工具是否真的可用**，不看平台名——同一平台的不同版本能力可能不同，
也可能因配置只开放部分能力。探测结果记 timeline：`平台档位=A（依据：<具体工具名>）`。
**探测结论与 §2.4 档案冲突时，以实际探测为准**，并把差异记一笔经验（项目 LESSONS 或本 skill）。

### 2.3 档位 → 执行方式映射

| 事项 | A 团队模式 | B 子代理模式 | C 单 agent |
|---|---|---|---|
| 角色任务（设计/美术/实现/QA） | 每角色 / 每卡启动具名成员并行 | 每卡派发一次子代理并行 | 主控顺序执行，切角色须声明 |
| 只读调研 | 同步子代理（如有）或成员 | 子代理 | 主控自己做 |
| 交接通道 | 消息 **+** 文件（**以文件为准**） | **仅文件** | 仅文件 |
| 派发提示词 | 可稍后追问补充 | **必须一次自包含到底**（无追问渠道） | — |
| 收割 | 等成员汇报 → 打开产出文件核验 | 调用返回 → 打开产出文件核验 | 自检 + 独立审读 |
| 阻塞 / 追问 | 成员报主控，主控统一问用户 | 子代理返回后在产出里写明 | 主控自查 |
| 并行度上限 | 受平台成员数限制 | 受并发调用数限制 | 1 |

**B 档与 A 档的关键差异**：B 档没有成员间消息通道，一切交接**只能落文件**；
派发词必须比 A 档更自包含，主控需等调用返回后再推进，不能指望"中途追问成员"。

### 2.5 CodeBuddy 参考实现（A 档）

> CodeBuddy 的多 agent 工具族：`task`（同步子代理 / 异步团队成员两种形态）、
> `send_message`（成员间通信）、团队创建与销毁。参数细节以平台当前文档为准，
> 以下固化的是**选型、协议与纪律**——这些不随参数名变化。
> **其他平台若同属 A 档**：照搬本节的协议与纪律，只把工具名换成该平台的对等能力即可。

#### 2.5.1 两种形态与选型

| 形态 | 怎么启动 | 行为特征 | 适用 |
|---|---|---|---|
| 同步子代理 | `task` 不带成员名，一次性调用 | 阻塞直到返回最终结果；每次全新上下文；结论直接回到主控 | 只读调研 / 代码探索 / 检索 / 评审——S1 现状调研、拆单可行性摸底、QA 素材收集、复盘数据核对 |
| 异步团队成员 | `task` 带成员名（团队模式） | 调用**立即返回**，成员后台工作；对话历史持久，可 respawn 续聊；经 `send_message` 通信 | 写文件的角色任务——设计 / 美术 / 实现 / QA；长生命周期、多轮交互、并行推进 |

选型口诀：**只读用同步，落盘用团队；调研先行，派发在后**——同步调研的结论先拿到手，
再一次性注入团队成员的派发提示词（§4 模板 A 的"输入文件清单"里直接给结论出处）。

#### 2.5.2 角色 → 成员映射

| skill 角色 | CodeBuddy 承载 | 成员命名规范 | 推荐 mode | 说明 |
|---|---|---|---|---|
| 主控 | 主会话（团队中的 `main`） | — | — | 全局唯一视角，独占 INDEX / 任务板 / 门禁 |
| 策划 | 团队成员 | `designer` | `default` | 可能需要向用户澄清，保留审批流 |
| 程序 ×N | 团队成员（按波次 spawn 或复用） | `prog-t03`（角色-卡号） | `acceptEdits` | 文件编辑自动接受，命令执行仍走审批 |
| 美术 | 团队成员 | `artist` | `acceptEdits` | 与 breakdown 并行启动 |
| QA | 团队成员 | `qa` | `default` | 执行测试命令需要审批把关 |
| 只读调研 | 同步子代理（内置探索型 agent） | 无需命名 | 只读 | 用完即走，不占团队 |

约定：

- **团队名 = WS-ID**（如 `ws-20260913-daily-shop`），**成员名 = 角色-卡号**——
  检索与复盘时一眼可见"哪个成员服务哪张卡"。
- `subagent_name` 从当前环境可用列表选择：只读任务优先内置探索型 agent；
  写任务选择具备写权限的 agent 类型（通常为用户自定义 agent）。
  **环境中不存在可写 agent 类型时**：按 §1 第 5 条退化为主控顺序执行 + timeline 留痕，
  不得硬派只读 agent 去做写任务。
- `mode` 选择原则：纯文档产出用 `acceptEdits`；涉及执行命令 / 跑测试 / 改公共代码用
  `default`；`plan`（先出方案待批）用于高风险卡——公共底座、删改历史数据、批量重构；
  `bypassPermissions` **仅用户明确授权时**使用，使用事实记入 timeline。
- `max_turns`：粒度明确的单卡任务可设回合上限防成员跑飞；不设上限的成员，
  派发词中必须写明"连续 2 次尝试失败即停"（与 §6 一致）。

#### 2.5.3 通信协议

| 动作 | 谁发起 | 怎么做 | 要点 |
|---|---|---|---|
| 派发 | 主控 | 首次 spawn 的提示词；后续追加指令用 `message` | 自包含：WS-ID + 角色 + 必读文件 + 任务 + 边界 + 输出文件 |
| 汇报 | 成员 | `message` → `main` | 状态(done/blocked) + 产出文件路径 + 关键证据 + 遗留问题 |
| 请示 | 成员 | `message` → `main` | 卡外发现、验收标准疑义、需要用户输入——不擅自处理 |
| 广播 | 主控 | `broadcast` | 设计冻结、阶段切换、全员工况变化；少用，重要决定仍须落 timeline |
| 计划审批 | 主控 ↔ 成员 | 成员(mode=plan) 先出计划 → 主控批准或驳回 | 批准后才动手；驳回意见必须具体到"缺什么"，不许只说"不行" |
| 关闭成员 | 主控 | `shutdown_request` → 成员 approve | 阶段收口后关闭空闲成员，不养闲成员 |
| 销团 | 主控 | 清理团队（如 team_delete） | WS 置 `closed` 后执行 |

澄清链纪律：成员需要用户输入时一律报主控，由主控**一次性集中**向用户提问——
多个成员各自向用户发问 = 挤牙膏式打扰，违反 S0 就定下的沟通纪律。

#### 2.5.4 等待与收割纪律（主控必守）

- **spawn 回执 ≠ 完成**。团队模式的调用立即返回，只代表成员已启动；
  把"已派发"当"已完成"写进任务板 = 数据造假。
- 派发后主控不空转等待：继续维护任务板、核验已完成的卡、过其他门禁、推进其他 WS；
  成员汇报到达后再核验收割。
- 收割三步：读成员汇报 → **打开产出文件**逐条比对验收标准 → 通过才置 `done` 并记 timeline。
  只读汇报摘要就打勾 = 主控失职。
- 同步子代理调用会阻塞主控：把同步调研放在异步派发**之前**完成，结论注入派发提示词；
  不要 spawn 了一堆成员，自己却卡在同步调用上。

#### 2.5.5 团队生命周期

```
开团（WS 进入 breakdown/dev，团队名 = WS-ID）
  → 按阶段 spawn 成员（S2A 主控拆单 ∥ S2B artist；S3 波次 prog-t##；S4 单人收口；S5 qa + 修复 prog）
  → 通信 / 核验 / 收割（§2.5.3–2.5.4）
  → 阶段末 shutdown 空闲成员
  → 下一阶段复用存活成员或重新 spawn（打回重做优先 respawn 同名成员：历史保留，省上下文重建）
  → WS closed 后销团
```

## 3. 并行 / 串行调度图（按平台档位执行）

> 下图按 **A 档（团队模式）** 示例标注。**B 档**把"成员 / spawn"读作"子代理 / 派发"，
> **C 档**读作"主控顺序执行该角色"——调度结构与并串行关系**跨平台不变**。

```
intake(S0) → design(S1)          ← 主控；S1 现状调研先派同步子代理，再 spawn designer 成员
                 │ G1
        ┌────────┴────────┐
        ▼(并行)            ▼(并行)
  breakdown(S2A)      art(S2B)          ← 主控拆单 ∥ spawn artist 成员，两路同时推进
        │ G2              │ G2'
        └───────┬─────────┘
                ▼
   implement(S3)：按 DAG 分波 spawn prog-t## 成员
     波次 = 拓扑排序的"就绪层"（依赖全 done 且互不冲突的卡）
     示例：[T01 公共底座] → [T02 T03 T04 并行=3 成员] → [T05 T06] → [T07 接入准备]
                │ G3 逐卡
                ▼
   integrate(S4)：spawn 单 prog 成员收口（串行，需要全部前置齐备）
                │ G4
                ▼
   qa(S5)：spawn qa 成员执行；BUG 由主控登记，
           修复卡按 S3 波次规则并行 spawn prog 成员，回归由 qa 成员收口
                │ G5
                ▼
   ship(S6) → retro(S7)：主控串行（数据核对可派同步子代理）
```

**判并行三条件（缺一不可）**：依赖已满足（DAG）∧ touches-files 无交集 ∧ 验收可独立判定。
不满足就串行——**串行不是失败，返工才是**。

## 4. 派发提示词模板（主控必须按此结构注入）

### 模板 A：派发执行者（A 档团队模式；B 档子代理沿用同一结构，写文件任务）

```
你是「<角色>」，为工作流 <WS-ID>（<一句话需求>）工作。你的成员名：<角色-卡号>。

## 第一步：开工前必读（按序）
1. 本 skill 的 references/roles.md 中「<角色>」章程（职责/禁做/准则）
2. <输入文件清单，含路径；调研类结论直接粘贴或注明出处文件>
3. references/knowledge/lessons.md 中标签含「<阶段>」的条目

## 任务
<具体任务描述；若是任务卡：完整粘贴任务卡内容>

## 边界（硬约束）
- 只允许写这些文件：<明确清单>；禁止修改 INDEX.md / 02-task-board.md / 其他任务卡
- **并发写约定**（若与他人共享某文件，必填）：只写本卡区段 <区段描述>，其余部分只读；
  改前重新读取该文件最新内容，禁止整文件重写 / 格式化 / 跨区重排，
  提交前 `git diff` 自检只含自己改动（§5.2 四道防线）
- **编号**：不得自行取 `T##` / `BUG-###` / `D-xx` / `L-xxx`，需要新编号时向 main 申请（§5.3）
- 代码提交信息格式：[<WS-ID>][<T##>] 摘要
- 只做任务范围内的事；发现卡外问题 → 报 main（或写入产出文件"发现与建议"节），不顺手处理
- 阻塞判定：连续 2 次尝试失败即停止，向 main 汇报已试方案，不要硬编

## 产出要求
- 按模板写入：<输出文件路径>
- 完成后向 main 汇报：状态(done/blocked) + 做了什么 + 证据（命令输出/文件路径）+ 遗留问题
```

派发参数建议：`mode` 与 `max_turns` 按 §2.2 角色表与约定执行。

### 模板 B：调研子任务（只读；A 档同步子代理 / B 档子代理）

```
为工作流 <WS-ID> 的 <阶段> 做只读调研，产出一段自包含结论（该结论将注入后续派发提示词）。
问题：<具体问题：系统现状 / 某模块行为 / 某配置在哪定义>
范围：<目录/模块>；只读，不改任何文件。
输出：结论 + 关键文件路径与行号级证据 + 对 <后续工作> 的影响点。
彻底程度：quick / medium / very thorough（按问题大小选）。
```

## 5. 冲突规则（并发写同一文件的正确性保障）

> **前提认识**：被派发的执行者（A 档成员 / B 档子代理）之间的并发是**约定级**的——
> 平台通常不提供系统级文件锁，两个执行者同时写同一文件不会有任何一方被自动拦住。
> 因此默认策略是**不并发写**；确需并发写同一文件时必须套用 §5.2 的四道防线。
> 并发写是**例外**，不是常态（C 档只有一个执行者，本节自然不适用）。

### 5.1 派发前互斥检查（防线零：串行优先）

- 主控责任：即将并行的卡两两比对 touches-files；有交集 → 串行化（标依赖）或合并为一卡。
- **公共配置表 / 公共组件类文件默认高危，涉及它们的卡一律串行**（见 lessons L-004）。
- 任务卡应区分两类文件：**独占文件**（owner = 本卡）与**共享文件**（需按 §5.2 分区）。

### 5.2 确需并发写同一文件时：四道防线（缺一不可）

仅当业务上无法串行化（如两张卡都要往同一张公共表加各自的字段 / 注册表加各自的条目）才启用，
且**必须由主控在派发前完成约定并写进派发词**：

| 防线 | 要求 | 谁负责 |
|---|---|---|
| ① 分区所有权 | 主控为每个成员划定**可写区段**（如"仅 `Section: shop_items` 段内""仅第 40–60 行的 X 区块"），区段之间互不重叠，其余部分**只读** | 主控（派发前） |
| ② 只追加不重排 | 成员在自己区段内**只做新增或改局部值**；禁止整文件重写、格式化、换行符统一、跨区移动或重排——重排会让另一方的行号锚点失效 | 成员 |
| ③ 写前重读 | 动手前必须**重新读取该文件当前磁盘内容**（不得以派发时的快照为准，期间可能已被他人改动）；改完立即复核自己那段的 diff，确认没吞掉他人改动 | 成员 |
| ④ 版本控制兜底 | 变更必须发生在 git 工作区内；提交前 `git diff <文件>` 自检只含自己的改动；发现被覆盖 → 用 git 定位恢复，以先提交者为准，后者基于最新内容重做差异（见 5.4） | 成员 + 主控 |

> 四道防线缺任何一道，**不允许并发写**，退回串行（主控重排波次或合并卡）。

### 5.3 追加式文件的并发约定（timeline / LESSONS 等）

追加式文件天然允许多人 / 多 agent 并发追加，但仍须守住三条：

1. **ID 取号主控独占**：`T##` / `BUG-###` / `D-xx` / `L-xxx` 的取号只能由主控执行，
   成员不得自行取号——两个成员同时"取当前最大 +1"必然撞号。
2. **只许尾部追加，不改已有条目**：要更正历史内容 → 追加"更正条目"（与铁律 2 一致）。
3. **格式与署名一致**：每次追加自带时间戳 + 署名（成员名 / 人名），沿用同一套条目格式。

### 5.4 运行中越界与撞车处置

- **运行中新增文件**：实际改了 touches-files 之外的文件 → 立即回填任务卡并报主控；
  若与他卡撞上 → 后提交者停下，主控裁决（rebase / 串行重做）。
- **已发生覆盖**：以先提交者为准，后者基于最新内容重做自己的差异部分；
  两者都记 timeline；被吞掉的改动**用 git 找回，不得凭记忆重写**。
- **成员发现冲突隐患**：立即停手报主控，不自行"顺手合并"——顺手合并 = 复盘时说不清的 diff。

### 5.5 独占文件与全局锁

- **独占文件**（不做并发，唯一 owner）：`INDEX.md`、`02-task-board.md`、他人任务卡、
  `01-design.md`、`03-art-design.md`。其他成员对这些文件的需求走"变更申请"，由 owner 落地。
- **任务板锁**：并行期间任务板状态列由主控统一更新，成员只在自己卡内写状态日志；
  成员对任务板的任何直接修改 = 越权，主控回滚并留痕。
- **美术回流**：art 期间产生的程序配合需求 → 只能经主控增量拆单，
  美术成员不得直接给程序成员派活。

## 6. 失败与超时处理

| 情形 | 处理 |
|---|---|
| 子 agent 执行失败 / 输出不合模板 | 主控不直接重试原提示词：先补上下文（缺了什么信息导致失败），再重派；连续 2 次失败 → 任务 `blocked`，换方案或换执行者 |
| 团队成员无响应 / 长时间无产出 | 主控 `shutdown_request` 关闭后 respawn 同名成员（历史保留），派发词附"从 <文件> 继续"；仍无产出 → 按 `blocked` 处置 |
| 派发失败（A 档 spawn 失败 / B 档子代理调用失败）/ 环境无可写权限的执行者 | 按 §1 第 5 条退化：主控顺序执行 + timeline 记录"多 agent 不可用，已退化（档位=C）"；不得硬派只读 agent 做写任务 |
| 子 agent 越权写了禁写文件 | 主控回滚该文件（git），timeline 记录越权事实与原因，重派时强化边界 |
| 任务阻塞 >1 个工作日 | 主控必须处置：拆小卡 / 换人 / 升级为设计问题 / 暂停 WS 并记录 |
| 并行撞车已发生 | 以先提交者为准，后者基于前者重做差异部分；两者都记 timeline |
| 执行者是人 | 同样规则：阻塞即标 `blocked`，AI 主控在 timeline 追踪并定期提醒 |

## 7. 人工介入点（默认配置，CONFIG.md 可改）

| 门禁 | 默认 | 原因 |
|---|---|---|
| G1 设计评审 | **人工确认** | 设计质量决定下游全部成本，且含价值判断 |
| G5 发布验收 | **人工确认** | 上线风险承担在人 |
| 其余门禁 | AI 主控自检 + 留痕 | 机械性检查，AI 可靠 |

人工门禁的执行方式：主控汇总门禁清单与证据 → 请用户逐项确认 → 用户答复记入 timeline
（谁、何时、通过/打回及意见）。**用户未答复前视为未通过，主控不得自行推进。**

补充：执行者的"先出方案待批"机制（A 档为 `plan` 模式，其他平台取等价能力）是门禁的
**前置手段而非替代**——高风险卡先出方案、主控批准后再动手；
G1/G5 的人工确认不因已用过方案审批而豁免。

## 8. 一人多角 / 人机混合的补充规则

- 同一 AI 会话先后扮演主控与执行角色时，切换角色必须显式声明（timeline 记"角色切换"），
  且执行产出仍需以主控视角重新审读后再过门禁。
- 主会话天然就是主控（A 档团队中通常名为 `main`）。"一人多角"的两种形态：
  - **C 档 / 退化场景**（§1 第 5 条允许）：主会话串行扮演各角色，每次切换显式声明；
  - **A / B 档（有派发能力）**：主控不再亲自扮演以回避角色冲突，改派执行者。
    主控亲自执行某张卡会让"独立审查"失效（自己写的卡自己审 = 没审），
    此时该卡评审须指定其他执行者或人工。
- 人执行任务卡时，AI 负责提醒流程（提交前缀、回填字段），不代人填写自测证据。
